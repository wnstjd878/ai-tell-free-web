# SKELETONS.md — 뼈대 9종 (화면마다 골라 쓰는 판)

`VISUAL-RULES.md`의 9규칙이 **품질**을 지킨다면, 이 파일은 **인상**을 담당한다. 9규칙만 지키면 밤티(AI 티)는 안 나지만 모든 화면이 똑같이 생기게 된다. 그래서 뼈대는 화면 성격에 따라 9개 중 하나를 고른다.

**살아 있는 견본은 같은 폴더의 `SKELETONS.html`.** 브라우저로 열면 9종이 같은 내용으로 위아래 나란히 렌더링된다. 고른 뼈대의 CSS 블록과 마크업을 그대로 떼어 쓴다. 글로 읽고 해석하지 말고 파일을 열어서 보고 고른다.

## 고르는 표

| 뼈대 | 판 | 제일 큰 글자 | 밀도 | 이럴 때 |
|---|---|---|---|---|
| `sk-report` 리포트 | 회색 바탕 위 흰 카드, 카드 안에서 단계 구분 | 25px 제목 | 보통 | **고민되면 이것.** 어디 넣어도 무난한 기본값. 사장님 대시보드·운영분석 |
| `sk-editorial` 에디토리얼 | 카드 없이 흰 종이 + 굵은 가로선 | 40px 제목 2줄 | 낮음 | 읽히는 화면. 공개 보고서, 랜딩 |
| `sk-data` 데이터 | 잉크색 머리 + 촘촘한 표, 회색 띠로 묶음 | 22px 흰 제목 | 높음 | 어드민, 관제탑. 항목이 많고 숫자를 세로로 훑을 때 |
| `sk-split` 스플릿 | 좌우 비대칭 2단 (37:63), 왼쪽 잉크 패널 고정 | 34px 수치 | 보통 | 대상이 하나인 상세 화면. 스크롤해도 결론이 안 사라져야 할 때 |
| `sk-hero` 히어로 수치 | 위에서 아래 1단, 카드 없음, 굵은 가로선 | 78px 수치 | 낮음 | 첫 화면, 공유용 보고서. 숫자 하나가 메시지일 때 |
| `sk-timeline` 타임라인 | 세로선 + 점, 단계가 위에서 아래로 | 26px 제목 | 보통 | 순서·진행이 있는 작업. 지금 어느 단계인지 보여야 할 때 |
| `sk-mosaic` 모자이크 | 6칸 그리드에 4·3·2칸 타일 비대칭 | 27px 수치 | 높음 | 훑어보는 대시보드. 항목이 여럿이고 무게가 다를 때 |
| `sk-qa` 문답 | 질문 블록 연속, 굵은 가로선 위아래 | 27px 질문 | 낮음 | 컨설팅·상담형. 설명이 필요하고 사용자가 궁금해할 때 |
| `sk-landing` 랜딩 | 큰 히어로 + 회색/잉크 밴드 + 카드 그리드 | 44px+ 헤드라인 | 보통 | 서비스 소개·가입 유도 메인페이지. 보고서 뼈대(1~3)를 랜딩에 쓰지 말 것 |

비슷해 보이는 것끼리 구분:

- `sk-report` vs `sk-mosaic`: 둘 다 카드지만 리포트는 카드 **한 장 안에서** 단계를 나누고, 모자이크는 카드를 **크기 다른 타일 여러 장**으로 흩는다. 항목이 3개 이하면 리포트, 6개 이상이면 모자이크.
- `sk-editorial` vs `sk-hero`: 둘 다 카드 없는 흰 종이지만 에디토리얼은 **글자**가 크고(40px 제목), 히어로는 **숫자**가 크다(78px). 메시지가 문장이면 에디토리얼, 수치면 히어로.
- `sk-editorial` vs `sk-landing`: 둘 다 큰 글자지만 에디토리얼은 **읽는 보고서**(가로선·1단), 랜딩은 **파는 메인페이지**(밴드 대비·카드·CTA). 정보 전달이면 에디토리얼, 가입 유도면 랜딩. 보고서 뼈대로 랜딩을 만들면 내부 화면처럼 나온다(실제로 겪은 사고다).
- `sk-data` vs `sk-timeline`: 둘 다 세로로 이어지지만 데이터는 **동등한 행**의 나열, 타임라인은 **순서 있는 단계**다. 순서가 의미 없으면 데이터.

한 서비스 안에서 화면마다 다른 뼈대를 써도 된다. 오히려 그게 정상이다. 대시보드는 모자이크, 매장 상세는 스플릿, 공개 보고서는 히어로, 컨설팅 결과는 문답 식으로 갈라 쓰면 같은 톤 안에서 화면마다 인상이 달라진다.

**같은 화면에 두 뼈대를 섞지 않는다.** 화면 하나에 하나만 고른다.

## 뼈대마다 갈리는 6가지

뼈대를 새로 만들 일이 생기면 이 6개 축을 바꾼다. 여기 말고 다른 데(색·글자 계층·여백 단계)를 건드리면 밤티가 돌아온다.

| 축 | report | editorial | data | split | hero | timeline | mosaic | qa |
|---|---|---|---|---|---|---|---|---|
| 판 | 카드 1장 | 세로 1단 | 잉크머리+표 | 좌우 2단 | 세로 1단 | 세로선+점 | 타일 그리드 | 질문 블록 |
| 구획 | 흰 카드 | 굵은 가로선 | 회색 띠+행선 | 잉크 패널 | 굵은 가로선 | 선 위의 점 | 타일 크기차 | 굵은 가로선 |
| 제일 큰 글자 | 25px 제목 | 40px 제목 | 22px 제목 | 34px 수치 | 78px 수치 | 26px 제목 | 27px 수치 | 27px 질문 |
| 섹션 제목 | 번호+명사 | 번호+명사 | 번호+명사 | 명사 | 영문 소라벨 | 단계+시점 | 타일 라벨 | 질문 문장 |
| 결론 위치 | 가운데 | 가운데 | 가운데 | 왼쪽 고정 | 맨 위 | 맨 아래 | 가운데 띠 | 두 번째 질문 |
| 밀도 | 보통 | 낮음 | 높음 | 보통 | 낮음 | 보통 | 높음 | 낮음 |

`sk-landing`은 정보 화면이 아니라 마케팅 판이라 위 6축 비교에서 뺐다. 고정 규칙(색은 판정에만+액센트 1색, 글자 계층, 여백 3단계, 이모지 금지)은 동일하게 적용되고, 형광펜 강조(잉크 글자+노랑 밑칠)는 랜딩 핵심 수치 1~2곳에만 허용한다.

앞의 셋(report·editorial·data)은 "1. 이렇게 읽었습니다 → 2. 겹쳐 보니 → 3. 그래서 이렇게" 라는 같은 흐름 위에서 껍데기만 다르다. 뒤의 다섯은 흐름 자체가 다르다. **한 서비스에서 앞 셋 중 둘을 같이 쓰면 비슷해 보이므로, 여러 화면에 변화를 주고 싶으면 뒤 다섯에서 고른다.**

## 다섯 다 고정인 것 (건드리면 밤티)

`VISUAL-RULES.md` 9규칙이 그대로 적용된다. 뼈대를 바꿔도 이건 안 바뀐다.

- 제목은 검정(`--ink`). 브랜드색으로 칠하지 않는다
- 색은 판정에만. `--accent`는 버튼과 순서 번호, `--pos`는 좋다는 수치
- 글자 단계 6개 이상 (머리말 / 큰제목 / 설명 / 소제목 / 라벨 / 수치)
- 라벨 왼쪽, 숫자 오른쪽 끝 정렬 + `tabular-nums`
- 여백 8 / 20 / 40 세 단계
- 좌측 색 세로바는 화면당 1곳 (핵심 발견에만)
- 이모지 배지 금지, 아이콘 라이브러리 기본값 금지
- 수치 옆에 근거·표본 표기

## 폰트

기본은 Pretendard 800이다. `sk-hero`의 78px 수치, `sk-editorial`의 40px 제목, `sk-qa`의 27px 질문, `sk-split`의 34px 수치처럼 **글자 자체가 화면의 주인공인 자리**에만 Paperlogy를 예외로 쓴다(`SKELETONS.html`에 그렇게 들어있음). 본문·라벨·수치 전반에 Paperlogy를 깔지 않는다. 기본 원칙은 "본문·헤드라인 모두 Pretendard, 포스터 톤일 때만 Paperlogy"이고 이 예외가 그 "포스터 톤"에 해당한다.

Paperlogy를 안 쓸 거면 해당 자리를 Pretendard 800 + `letter-spacing:-.05em`로 바꾼다. 크기는 그대로 둔다.

## 쓰는 절차

1. 화면 성격을 보고 위 표에서 뼈대 1개를 고른다
2. `SKELETONS.html`을 열어 그 뼈대가 맞는지 눈으로 확인한다
3. 해당 CSS 블록과 마크업을 프로젝트로 복사한다 (색·간격은 전부 CSS 변수를 참조하므로 그 프로젝트의 톤이 자동으로 따라온다)
4. 내용을 실제 데이터로 갈아끼운다. **빈 상자를 먼저 만들고 채우지 않는다**
5. `VISUAL-RULES.md` 맨 아래 자가 점검 7개를 대조한다

## 왜 이 파일이 있나

9규칙만 적용한 안 3개(report·editorial·data)를 만들었더니 셋 다 "위에서 아래로 1-2-3 섹션"이라는 같은 판 위에 껍데기만 바뀐 상태였고, 획일적이라는 지적을 받았다. 그래서 판 자체가 다른 5개(split·hero·timeline·mosaic·qa)를 추가해 8종이 됐다.

밤티를 막는 것과 화면이 지루해지는 것은 다른 문제다. 전자는 규칙(`VISUAL-RULES.md`)으로 막고, 후자는 뼈대를 여러 개 두고 돌려쓰는 것으로 푼다. 그래서 이 두 파일은 층이 다르고, 뼈대를 늘릴 때 규칙을 건드리지 않는다.
