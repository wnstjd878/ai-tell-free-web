# WRITING.md · 화면에 나가는 한국어

화면 문구를 쓰기 전에 읽는다. CSS 변수가 색을 정하고 VISUAL-RULES 가 짜임새를 정한다면,
이 문서는 **글자**를 정한다.

## 규칙의 출처

AI 티가 나는 글 패턴은 두 곳에 정리돼 있다. 여기서 다시 만들지 않고 그걸 가져다 쓴다.

- **`HUMANIZE-KO.md`** (같은 폴더). [blader/humanizer](https://github.com/blader/humanizer) (MIT, 위키백과
  "AI 글의 신호") 의 35패턴을 한국어 글에 맞게 옮긴 것. 부풀림, 홍보 어투, 출처 흐리기, 대화창 잔여,
  없는 반박에 답하기, 가짜 대안 같은 **내용과 태도**의 패턴이다. 괄호 숫자는 그 문서의 패턴 번호.
- **im-not-ai** (MIT). https://github.com/epoko77-ai/im-not-ai
  `skills/humanize-korean/references/quick-rules.md` 의 10분류 70패턴. 번역투, 이중 피동, 연결어미
  뒤 쉼표, 종결어미 반복 같은 **한국어 문법**의 패턴이다. `git pull` 로 갱신된다.

이 문서는 그중 **화면 문구에서 반복해서 걸리는 것만** 추린 것이다.

## 걸리면 고칠 것

| 걸리는 것 | 왜 | 대신 |
|---|---|---|
| 긴 줄표 `—`, 짧은 줄표 `–` | 영어 부가 설명 습관 (14, im-not-ai J-3) | 쉼표, 괄호, 또는 문장을 나눈다 |
| 줄 머리의 `•` `·` `▶` | 목록 장식 | 줄바꿈이나 번호 |
| `━━` `═══` 같은 강조선 | 화면에서 소음만 된다 | 여백이나 구분선 요소 |
| 그림글자(이모지) | (18, im-not-ai C-5) | 뺀다. 사용자가 달라고 하면 그때 |
| 혁신적·획기적·차별화된·진정한 | 뜻이 없는 과장 (4, im-not-ai D-4) | 무엇이 어떻게 달라지는지 사실로 |
| 결론적으로·정리하자면·한마디로 | 결산 상투구 (im-not-ai D-1) | 바로 결론만 |
| 지금 바로 시작하세요·더 알아보기 | 어디에나 있는 단추 문구 | 그 단추가 무엇을 하는지 |
| 손쉽게·간편하게 | 아무것도 안 알려 준다 | 몇 번 만에 되는지 |
| 카드 제목이 물음·말투 ("어디서 나갔나", "누가 벌어주나", "돈 나갈 일 · 막힌 일") | 화면이 어수선하고 메뉴·표 머리와 결이 어긋난다 | 두 어절 명사구 ("이탈 지점", "가입자별 수익 기여", "처리 대기 현황"). 짝 표는 `CARD-TITLES.md` |
| 도움이 되셨길·궁금한 점이 있으시면·언제든지 문의 | 대화창 맺음말이 안내문·빈 화면·알림에 남은 것 (20) | 뺀다. 문의 창구가 있으면 그 이름과 단추 |
| 좋은 질문입니다·물론입니다 | 아첨·맞장구 (22) | 바로 답만 |
| 살펴보겠습니다·알아보겠습니다 | 다음 내용 예고 (28) | 바로 내용부터 |
| 핵심은·본질은·진짜 문제는 | 평범한 말을 숨은 진실처럼 (27) | 그 문장을 바로 쓴다 |
| 솔직히 말하면 | 가짜 솔직 도입 (33) | 바로 답만 |
| 단순한 X가 아닙니다·X 그 이상·오해하지 마세요 | 글에 없는 반박에 답하는 틀 (34) | 무엇인지, 무엇을 하는지만 |
| 흔히 X를 고르지만·쉬운 방법은 X지만 | 아무도 안 고를 선택지를 세워 물리치는 틀 (35) | 실제 선택지와 제약만 |
| A가 아니라 B (여러 카드에 반복) | 한 화면에 하나면 사람 글, 반복되면 틀 (9, im-not-ai C-8) | 나머지는 직접 단언으로 |
| 밝은 미래·앞으로도 기대 | 뻔한 긍정 결말 (25) | 마지막 사실로 끝낸다 |

문장 안의 가운뎃점(`주문·배송·상품`)은 한국어 표준 부호라 그대로 쓴다. 금지 대상은
목록 머리표로 쓰는 경우다.

## 어디에 적용하나

**적용**: 화면 글자, 단추, 안내문, 오류 문구, 메일·알림 본문, 어드민 화면, 시트·보고서처럼
사람이 읽는 산출물.

**비적용**: 코드 주석, 변수·함수 이름, 서버 기록(`console.*`), 개발자에게 던지는 오류
(`throw new Error`), git 메시지. 그 자리는 정확한 기술 용어를 그대로 쓰는 게 맞다.

## 기계로 잡는다

글로만 적어 두면 지켜지지 않는다. 도구가 둘 있다. 보는 대상이 다르다.

**소스 코드 안의 화면 문구**는 `tools/screen_copy.py` 가 본다.

```bash
python3 tools/screen_copy.py <프로젝트폴더>
python3 tools/screen_copy.py <프로젝트폴더> --strict   # 어휘까지 실패로
```

**사람이 읽는 글 파일**(칼럼, 보고서, 알림 본문, 상세페이지 문안, .md)은 `tools/humanize_check.py` 가 본다.
고치는 규칙은 `HUMANIZE-KO.md`.

```bash
python3 tools/humanize_check.py 글.md
python3 tools/humanize_check.py - < 글.txt              # 표준입력
```

둘 다 평소에는 경고로만 본다. **배포 직전에만 `--strict` 로 돌려 실패로 바꾼다.**
옛 프로젝트에는 쌓인 게 많아 처음부터 막으면 배포가 통째로 멈추기 때문이다.
종료 코드는 0 깨끗, 2 볼 것만 있음, 3 고칠 것 있음이라 배포 스크립트에 그대로 물릴 수 있다.

`고칠 것` 은 기호와 대화창 잔여라서 예외가 거의 없다. `볼 것` 은 어휘라서 업계 표준 용어면 그대로 둬도 된다
(광고의 "최적화", B2B 의 "솔루션"처럼 뜻이 정확한 자리). 판단 기준은 하나다.
**그 단어를 빼면 뜻이 안 통하는가.** 통하면 뺀다.

새 화면을 만들면 그 폴더만 지정해 돌려도 된다.

일부러 남기는 자리는 예외 표시를 단다. JSX 태그면 `data-copy-ok=""` 속성, 그 밖의
코드 줄이면 줄 끝에 `// copy-ok: 이유`. 파일 통째로는 머리 주석에 `screen-copy: off`.

## 쓰고 나서 한 번 읽는다

도구가 못 잡는 것이 더 많다. 다 쓴 뒤 소리 내어 읽고 이 셋만 본다.

1. 같은 어미가 세 번 이어지는가 (`~합니다`, `~합니다`, `~합니다`)
2. 문장이 다 비슷한 길이인가. 짧은 문장을 섞는다
3. 안 써도 뜻이 통하는 단어가 있는가

긴 글을 통째로 고칠 때는 `HUMANIZE-KO.md` 의 "고쳐 쓰는 과정" 네 단계를 따른다.
더 깊이 볼 때는 im-not-ai 의 진단 도구(`metrics.py`)나 yoonmoon(https://github.com/amondnet/yoonmoon)
을 쓴다. 둘 다 MIT다.
